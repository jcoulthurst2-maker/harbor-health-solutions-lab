# Solutions Lab v2 — Assessment Methodology

## Purpose

The Lab is an independent apprenticeship. It is not affiliated with or endorsed by AWS, Google, Microsoft, OpenAI, FinOps Foundation, NIST, OWASP, CNCF, or any other referenced organization.

Public professional frameworks are used as inspectable reference standards. The Lab's contribution is to combine those standards inside longitudinal, cross-functional engagements where business, technical, economic, operational, and human realities interact.

## Four Engines

### 1. Engagement Engine
Creates the operating world: organization, market, users, stakeholders, systems, data, architecture, economics, constraints, events, and changing conditions.

### 2. Mentor Engine
Models professional apprenticeship progression. The mentor demonstrates and narrates early, then shifts through questioning, review, and eventual silence as the learner becomes more independent.

### 3. Lens Engine
Selects the professional standards relevant to the problem. Not every framework is used in every engagement.

### 4. Evidence Engine
Records demonstrated work: queries, code, architecture, technical artifacts, decision logs, financial models, reviews, incident handling, adoption outcomes, and transfer performance.

## External Reference Lenses

### AWS — Well-Architected + immersive learning
Used for architectural tradeoffs, workload scoping, review discipline, specialized lenses, continuous improvement, and the learning pattern of customer problem → requirements → proposal → build → validate.

### Google Cloud — Well-Architected
Used to reinforce portable architecture reasoning across security, reliability, performance, cost, operations, sustainability, hybrid, and multi-cloud contexts.

### Google SRE
Used for SLOs, error budgets, monitoring, alerting, incidents, postmortems, capacity, release reliability, troubleshooting, and production operations.

### Microsoft — Cloud Adoption Framework + Applied Skills pattern
Used for business strategy, planning, readiness, governance, security, management, adoption, organizational operating standards, and performance-based workplace tasks.

### OpenAI-style applied deployment work
Used as a model for end-to-end technical-business work spanning discovery, technical scoping, architecture, prototyping/build, evaluation, production rollout, adoption, and measurable workflow impact.

### FinOps Framework
Used for technology economics: forecasting, unit economics, budgeting, architecture placement, usage/rate optimization, licensing/SaaS economics, and value tradeoffs.

### NIST AI RMF
Used whenever AI appears. Review follows Govern → Map → Measure → Manage rather than treating governance as a one-time compliance lesson.

### OWASP ASVS + API Security
Used for application and API security verification. Later engagements reference selected controls rather than awarding credit for generic “security considered” statements.

### CNCF performance-based assessment principle
Used to enforce the rule that technical competence requires successful hands-on execution, not explanation alone.

## Review Philosophy

### Scope first
Before applying a checklist, establish the workload/system boundary, lifecycle stage, business importance, production status, dependencies, and consequence of failure.

### Prioritize lenses
Select the 2–4 dimensions most material to the engagement rather than treating every framework as equally relevant every time.

### Evidence over self-report
The learner receives credit only for observable work or a defensible decision trail.

### Improvement over grades
Reviews produce:
- demonstrated capability
- remaining uncertainty
- technical/business debt
- improvement actions
- next evidence required for advancement

### Consequence matters
Some organizations return later. Earlier decisions may create technical debt, operational leverage, adoption problems, cost consequences, or reliability effects. The Lab evaluates whether judgment remains sound over time.

## Performance Requirements by Domain

### Data / SQL
Must query unfamiliar structured data, choose defensible denominators/segments, and communicate evidentiary limits.

### Python / automation
Must create, repair, or use working code in support of an engagement. Copying a known pattern without understanding does not meet Independent.

### APIs / integrations
Must successfully interact with or diagnose an unfamiliar interface, including authentication, request/response behavior, errors, and data contracts where relevant.

### Cloud / architecture
Must design and defend a system under explicit tradeoffs; later stages require working or high-fidelity deployed components, not diagrams alone.

### AI systems
Must justify whether AI belongs, build/evaluate a working approach when appropriate, measure behavior, account for cost/latency/reliability, define oversight, and address governance/security.

### Security
Must identify and verify relevant controls in implemented systems. Generic acknowledgement is insufficient.

### Reliability / SRE
Must diagnose production-style failures using observable signals, protect service objectives, recover appropriately, and produce learning/improvement artifacts.

### Economics
Must connect technology choices to cost, unit economics, forecast, or measurable business value without fabricating savings.

### Product / adoption
Must connect system behavior to user behavior and establish whether the intervention is actually useful and adopted.

### Organizational execution
Must understand ownership, governance, incentives, change, operating processes, and the conditions required for a solution to survive in an organization.

## Portfolio Evidence Standard

Public claims should link to evidence whenever possible. Suitable artifacts include:
- problem frame and decision log
- SQL queries and analysis outputs
- data dictionaries and evidence maps
- API traces and integration diagrams
- working code or deployed components
- architecture options and tradeoff records
- selected framework reviews
- threat/security checks
- SLOs, incident notes, and postmortems
- AI evaluation plans/results
- FinOps models and unit economics
- stakeholder/executive recommendations
- adoption/value verification
- retrospective and transfer analysis

## Integrity Rule

A result should never be presented as real-world customer impact when it is simulated. Simulated engagements may quantify modeled consequences, but public wording must distinguish simulation, model, benchmark, and actual deployed outcome.
